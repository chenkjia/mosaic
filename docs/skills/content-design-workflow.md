# 内容设计流程（通用骨架）

> 从卡牌项目（sanguoV2）的内容设计流程抽象而来：把创意输入收敛为经用户确认、可进入正式文档与后续 Matt Workflow 的**内容设计包**。适用于角色、关卡、道具、文案、奖励等一切内容生产。项目化时按内容类型填充分支与 schema 指针；卡牌项目完整先例见 sanguoV2 `docs/skills/content-design-workflow.md`。

## 1. 目标与边界

- 覆盖：新内容项、新规则单元、既有内容的平衡调整，以及玩法定位与视觉锚点的互相校验。
- 不覆盖实际出图与代码实现：图片生成与软件实施是后续任务，不作为本流程的隐含步骤。

## 2. 权威边界

参考目录（`docs/reference/`）是只读输入，不是生产数据源。冲突按以下优先级处理：

1. 根级和局部 `AGENTS.md` 的流程与技术约束；
2. `CONTEXT.md`、已有 ADR 和当前 schema；
3. 已确认的正式设计与运行时内容；
4. 参考目录中的资料；
5. 本次提案中的未确认内容。

新设计需要突破第 1-3 层时，必须先记录为待确认项；不得用参考资料默默覆盖正式约束。

## 3. 入口与分支

每个设计项从同一入口创建提案：`.scratch/content-design/<slug>/proposal.md`。元数据至少含：批次、入口分支、状态、负责人、依赖、拟用稳定 ID。入口分支由项目定义（卡牌先例：`new-character` / `new-skill` / `rebalance`；不得把调整伪装成新增以绕过兼容性检查）。

所有分支共享「来源审查 → 方向设计 → 机制定义 → 验证 → 生产确认 → 正式化 → handoff」；分支只改变中间的设计问题。

设计方向固定回答四个问题：玩家如何识别它；它希望玩家做出什么决定；它在系统中的职责；它的代价、限制或反制手段。

## 4. 提案固定结构

每份 `proposal.md` 使用以下顺序，没有内容的部分写「无」，不删标题：

- **A. 元数据**：批次、分支、候选名称与稳定 ID、状态、依赖、明确不处理的事项。
- **B. 来源审查**：表格逐条登记（来源文件、可复用事实、设计意图、与当前 schema 的冲突、处理决定）。参考内容必须标注「事实 / 历史设定 / 玩法建议 / 待核实」，不能整段当事实。
- **C. 设计方向**：上述四问。
- **D. 机制定义**：写成可测试规则（触发/时机、目标、效果、数值、成长、限制、边界行为、随机性）。描述必须能转换成确定的测试断言；「适当」「较高」「视情况」不得出现在最终机制字段中。
- **E. 视觉 brief**：方向确认前只写视觉锚点（主体色、识别要素、关键道具、姿态、一句话气质）；生产确认前补齐完整 art brief（外貌服饰、构图、材质、配色、动作帧、强制项、负面清单）。
- **F. 验证记录**：同类内容横向对比 + 边界场景表 + 对玩家决策与反制手段的检查 + 对 schema/CONTEXT/既有测试影响的检查。
- **G. 待确认项与变更记录**：逐条可回答并标明阻塞阶段；任何用户决定写入变更记录（日期 + 问题编号）。

## 5. 阶段与门禁

- **Stage 0 建立批次与审查来源**：完成来源清单、冲突表、范围/非范围、依赖与稳定 ID 候选。只读参考目录、CONTEXT、schema、ADR 与正式数据。完成条件：没有未标注来源的关键事实。
- **Stage 1 设计方向**：完成身份定位、职责、承诺、代价/反制与视觉锚点。
  - **Gate 1 `direction-confirmed`**：用户确认范围、定位、核心决策与视觉锚点后，才可进入完整机制与数值。
- **Stage 2 完整机制**：触发、目标、效果、数值、限制、交互与失败行为写成可测试规则；同步检查 schema 字段覆盖。
- **Stage 3 平衡与边界验证**：横向对比 + 场景表。命中以下任一条件时，必须补可重复原型或模拟：新时序、复杂目标选择、状态叠加、死亡/复活、跨回合效果、随机选择、多个钩子互相影响。随机验证必须可注入种子或随机函数。
- **Stage 4 生产包**：整理最终字段、数值、文本、art brief、验证结果与影响清单；关键待确认项清零。
  - **Gate 2 `production-confirmed`**：用户确认最终规则文本、数值、边界行为与 art brief 后，才允许正式化。
- **Stage 5 正式化**：按项目约束写入正式产物（批次设计文档、schema 化定义、数据源、art brief），遵守目标目录的局部约束；派生产物只跑现有转换脚本，不手改。状态 `formalized`。
- **Stage 6 移交 Matt Workflow**：建立或更新 REQ，附设计包全部产物。handoff 说明必须含：哪些是正式事实、哪些 ID 已固定、要实现的规则钩子与测试场景、明确不在本批次的事项、非阻塞风险。状态 `handed-off`。

handoff 后玩法实现问题回到 [`matt-workflow.md`](matt-workflow.md)；内容规则变更重新开调整提案，不直接改实现。

## 6. 完成检查表

- [ ] 入口分支与批次确定
- [ ] 来源逐条登记，参考与正式事实已区分
- [ ] CONTEXT / schema / ADR / 正式数据冲突已处理
- [ ] Gate 1 方向确认完成
- [ ] 机制可写成确定断言
- [ ] 横向对比与场景表完成
- [ ] 高风险机制完成可重复原型/模拟
- [ ] art brief 完成（实际出图不在本流程内）
- [ ] 待确认项清零或明确标记为非阻塞风险
- [ ] Gate 2 生产确认完成
- [ ] 正式产物、派生产物、验证记录已更新
- [ ] 已按 Matt Workflow 完成 handoff
- [ ] `logs/agent-activity.md` 已记录本次文档与决定
